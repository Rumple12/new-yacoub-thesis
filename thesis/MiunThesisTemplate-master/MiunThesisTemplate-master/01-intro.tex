\section{Introduction}\label{sec:intro}

This thesis investigates how a workflow automation system can be used as part of a small, measurable IoT-style action pipeline. The work focuses on a controlled temperature-to-fan scenario in which a workflow receives a temperature event, selects a fan action, passes the action through a structured contract boundary, calls Python middleware, and records evaluation evidence. The purpose is not to build a production IoT platform, but to examine whether a focused workflow-to-action architecture can be implemented and evaluated clearly.

\subsection{Background and Motivation}\label{subsec:background}

Workflow automation platforms are often used to connect triggers, decision logic, external services, and actions. In such systems, a workflow can receive an event, process it through configured nodes, and call an external endpoint. n8n is one such workflow automation platform and can be self-hosted for local experimentation and integration work \cite{n8nDocs,workflowPatternsAalst}. This makes it suitable for a thesis prototype where the workflow engine should be visible, configurable, and testable.

IoT-style systems often follow an event-action pattern: a sensor or test event is received, a decision is made, and an action is triggered. Edge hardware such as Raspberry Pi can also be used to place part of a system closer to a device or environment \cite{edgeComputingSatyanarayanan,iotSurveyAtzori,raspberryPiDocs}. However, when workflows or agent-enhanced workflow steps are allowed to trigger actions, the system needs more than a decision rule. It also needs a controlled action boundary, structured messages, validation, and evidence that the expected action was actually produced.

This thesis uses a fan on/off scenario as a controlled proxy for that broader problem. The fan itself is simple, but the architecture around it is the important part: a temperature event enters the workflow, the workflow selects or produces an action, the action is represented in a structured form, middleware executes a simulated endpoint, and the evaluation harness records the result. This allows the thesis to study a complete event-to-action path without expanding into a broad hardware or automation platform.

\subsection{Problem Statement}\label{subsec:problem-statement}

The problem addressed in this thesis is that an IoT-style workflow is not sufficiently evaluated by showing only that a workflow can make a decision. If a workflow or agent-enhanced step can trigger an action, the system also needs a clear boundary between workflow logic and action execution. Without such a boundary, it becomes difficult to explain which component made the decision, which component executed the action, and what structure the action message was expected to follow.

The thesis therefore treats the problem as an integration and evaluation problem. The system needs structured action messages, a documented validation design, a middleware layer that separates workflow decisions from action execution, CSV-based evidence for result reporting, and limited hardware-side validation. JSON contracts are used to make the sensor and action payloads explicit \cite{jsonSchemaDocs}. The problem is investigated within a controlled proof-of-concept rather than through a large-scale deployment.

\subsection{Aim}\label{subsec:aim}

The aim of this thesis is to design, implement, and evaluate a self-hosted n8n-based proof-of-concept for a temperature-to-fan IoT-style action pipeline using Python middleware, structured contracts, lightweight evaluation, and Raspberry Pi middleware validation.

The aim is addressed by implementing a deterministic baseline workflow, a minimal agent-enhanced workflow, shared JSON contracts, a minimum safety and validation design, simulated fan endpoints, a CSV evaluation harness, and a validation setup where the middleware/action endpoint runs on Raspberry Pi while n8n remains on the PC.

\subsection{Research Questions}\label{subsec:research-questions}

The thesis is guided by three research questions:

\begin{enumerate}
  \item \textbf{RQ1:} How accurately and consistently does the deterministic n8n workflow produce the expected fan action across the defined temperature test cases?
  \item \textbf{RQ2:} How accurately and consistently does the minimal agent-enhanced workflow produce contract-valid action output compared with the deterministic baseline?
  \item \textbf{RQ3:} What latency, resource, and deployment behavior is observed during local execution and Raspberry Pi middleware validation?
\end{enumerate}

No separate yes/no research question is created for safety. Instead, contract validity and the documented validation boundary are evaluated as part of RQ2 and discussed further in Chapter~\ref{sec:discussion}. This keeps the research questions measurable and aligned with the implemented system.

\subsection{Scope and Delimitations}\label{subsec:scope-limitations}

The defined scope includes a local PC-hosted n8n runtime using Docker, a Python middleware API, one temperature-event path, simulated \texttt{fan\_on} and \texttt{fan\_off} actions, a deterministic baseline workflow, a minimal agent-enhanced workflow, shared JSON contracts, a documented minimum safety and validation design, a CSV-based evaluation harness, and Raspberry Pi middleware/action endpoint validation. The middleware exposes \texttt{/status}, \texttt{/sensor-event}, \texttt{/fan/on}, and \texttt{/fan/off}.

The system is deliberately kept as a controlled proof-of-concept. Full n8n deployment on Raspberry Pi is outside the scope. Real GPIO fan or sensor hardware is outside the scope. Production-grade runtime safety enforcement is outside the scope. Broad multi-agent architecture, multiple models, multiple devices, and large-scale benchmarking are also outside the scope. These delimitations allow the thesis to focus on one complete and measurable workflow-to-action pipeline.

\subsection{Contributions}\label{subsec:contributions}

The technical contribution of the thesis is a complete temperature-to-fan proof-of-concept architecture that combines self-hosted n8n workflow orchestration, a Python middleware action boundary, deterministic and minimal agent-enhanced workflow paths, shared JSON contracts, a documented validation design, CSV-based evaluation, and Raspberry Pi middleware validation. The contribution is not a new IoT platform or a production safety system. It is a focused implementation and evaluation of a workflow-to-action pattern that can be inspected, measured, and discussed.
